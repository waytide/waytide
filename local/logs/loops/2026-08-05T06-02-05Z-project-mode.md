# Loop record — The project mode: formal or creative

The design of a project-level mode, chosen at initiation, deciding whether a project's planning artifacts are a **design** and a **plan** or an **aspiration** and an **intention**. The feature's lifecycle record is `waytide/local/features/2026-08-05T06-02-05Z-project-mode.md`.

**Mode: attended.** Chosen at initiation on 2026-08-04 beside the working location. The loop stops at every hinge and the developer deliberates each one, so every cycle below carries the options put at the gate and the decision that resolved it.

## Cycle 1 — where the mode is recorded and what reads it

**Hinge.** The mode decides which directory every planning artifact goes in for the project's life, so it has to be legible at the start of every session. Everything else in the feature rests on this; the prompt itself is mechanical by comparison.

**A finding that shaped the options.** Inferring the mode from which directories exist is **circular**: the first aspiration cannot be placed until the mode is known, and the directory only exists once something is in it — and git does not track an empty directory. So inference needs a placeholder file anyway, which makes it *a file exists* arrived at indirectly. That reduced the real decision to whether the mode is **stated or inferred**, and if stated, whether it lives in what the agent already reads or in something a script can parse.

**Options.** A local rule in `waytide/local/rules/`; a `**Mode:**` recognizable-content line in a dedicated file under `waytide/local/`, in the form `session-start.sh` already parses; or the presence of `waytide/local/aspiration/` itself.

**Decision.** **A local rule.** It introduces no mechanism: local rules are read unconditionally at the start of every session, and the mode genuinely **is** a binding convention of the project rather than a setting attached to one. It also puts the mode where the system already keeps things of its kind, which the recognizable-content line would not have.

**What the choice gives up**, recorded rather than re-argued: the mode is not machine-readable, so `session-start.sh` cannot report it in the notice without parsing prose. And changing mode means removing a binding rule, which the rules-convention makes a deliberate act with reconciliation attached — heavier than flipping a value, and arguably correct for a decision of this reach.

## Cycle 2 — what an absent mode rule means, and when the prompt fires

**Hinge.** Forced by cycle 1, and one question wearing two faces. If absence means formal, then choosing formal writes nothing and nothing distinguishes *asked and chose formal* from *never asked*, so the prompt has no way to know it has already fired. If the rule is always written, that is solved, but every project that already exists is prompted on its first session after the rule ships.

**Options.** Always write the rule and prompt once when absent; absence means formal with the prompt tied to the install; absence means formal with the prompt raised when the first planning artifact is about to be written.

**Decision.** Absence means formal, with the prompt tied to the install.

**This cycle's outcome did not stand.** The developer identified a silent failure in it, and cycle 3 replaced it. The cycle is kept as written because it happened, and because the defect is only legible against the choice that had it.

## Cycle 3 — the silent revert

**Hinge.** Raised by the developer against cycle 2's outcome: if the mode is creative, a creative mode rule is written, and that rule is then **accidentally deleted**, absence reads as formal — and formal expects `design/` and `plans/`. The project keeps working, incorrectly, with nothing announcing it: the agent writes to the formal directories while `aspiration/` and `intention/` hold the project's actual planning artifacts, and the project's planning splits across two vocabularies unremarked. It is the silent-failure class this system argues against everywhere else.

**What the agent contributed.** That the observation identifies a **missing check** rather than necessarily overturning cycle 2: the **directories are evidence**. A project holding `local/aspiration/` with no creative rule is a **contradiction**, not a formal project, and that is visible without any new mechanism. It is the same stance taken in the registry parser earlier the same day — refuse to misread rather than proceed on ambiguous input. Also noted, in fairness to the option the agent had not argued for: *always write the rule* degrades better on its own, a deleted rule there producing a re-prompt, which is loud rather than silent.

**Options.** Corroborate against the directories while keeping absence-means-formal; always write the rule **and** corroborate; always write the rule with no check.

**Decision.** **Always write the rule, and corroborate.** So:

- **Both modes write a mode rule** into `waytide/local/rules/`.
- **An absent rule means the question has never been asked**, not that the project is formal, so the agent asks — once.
- **The planning directories are checked against the rule.** `aspiration/` or `intention/` present with no creative rule, or a creative rule with only the formal directories populated, is a **contradiction**: the agent surfaces it and asks rather than assuming either mode.
- **The accepted cost** is the one cycle 2 had avoided: the four consuming projects in the registry and this repository are each prompted once, about a mode none of them is changing.

## Cycle 4 — what the two modes actually differ in

**Hinge.** Whether the creative mode gets its own conventions and document formats, or shares the formal mode's. The source observation had named the **doubling cost** — four `foundation` rules forked, every future rule naming these directories inheriting the obligation — as the risk that might sink the whole idea.

**Decision, given as direction.** **The conventions and document formats are the same.** Also settled in the same instruction: the mode **does not change after initiation** (to be considered further later), and the mode rule is named **`formal-mode`** or **`creative-mode`**, stating that the project operates under that mode and which conventions are active.

**What the agent surfaced, because it changes what the feature is.** The argument that made this two modes rather than two names was **supersession** — *nobody supersedes an intention*, and an aspiration is not measured by completion the way a plan is. **Identical conventions abandon that claim.** An intention is superseded exactly as a plan is, carries the same checkbox tasks, and is measured the same way. What differs is the vocabulary and the directory.

**That is the stronger position rather than a retreat, and the system's own rules say why.** `language-is-precise-here` holds that a word is the thought's working surface and choosing a word chooses a concept; `rules-install-a-mindset` holds that a large share of what a rule does is install a **stance**, and that vocabulary is the most direct lever on a mental model. A developer writing an *aspiration* is doing something different from one writing a *design*, and the difference is in them rather than in the document. The mode is that lever at the scale of a project. It is a different claim from the one the observation recorded, which is why the observation is reconciled rather than left to read as though it predicted this.

**A mechanical note.** A local rule takes the ISO-8601-UTC filename prefix, so the file is `2026-…Z-creative-mode.md` — the specified name is the name part. A useful consequence: the **filename alone carries the mode**, so both the never-asked check and the corroboration work without the file being opened.

## Cycle 5 — how the four conventions carry the mode

**Hinge.** `design-convention`, `plans-convention`, `design-document-format`, and `plan-document-format` name `waytide/local/design/` and `waytide/local/plans/` throughout. With the conventions shared, something still has to tell a creative project which directory it uses.

**Options.** The mode rule states the substitution once and the four are left untouched; each of the four is edited to name both; or the four stop naming directories at all and speak of the settled-direction and sequencing artifacts, with the mode rule binding those to paths.

**Decision.** **Edit the four to name both.** A reader of any one rule sees the truth for their project without having to know the mode rule exists. The cost accepted is that the mode is now stated in five places rather than one, and that a future rule naming these directories inherits the same obligation.

**What was built.** The `a-project-works-in-formal-or-creative-mode` rule in `foundation`; both directory conventions retitled and opened with the creative counterpart; both document formats retitled and stating that the creative document's shape is the same shape entirely; and the `foundation` README carrying the mode in its summary and in its work-artifact directory list.

## Cycle 6 — the mode rule's own text, worked through in five gates

**Hinge.** What the file written into a project's `waytide/local/rules/` actually says. The developer asked to work it through by question and answer, so it ran as five gates rather than one, each answer narrowing the next.

**How much it says.** Options: the fact plus why *this* project chose the mode; the fact alone; self-contained. **Self-contained** — the file restates what the modes are, which directories, that the conventions are identical, and why the mode exists, so a person reading only this project's rules understands it without leaving the file.

**What governs when foundation's rule is revised and the copy is not.** Options: name foundation as the authority; treat it as a dated snapshot; regenerate it on refresh. **A dated snapshot** — which is what a local rule already is, the file-names rule calling it a dated decision in that project's history.

**Which part binds.** The agent surfaced a consequence it had under-stated when putting the previous gate: it is not only a *reader* left without a stated winner — the **agent** reads both every session, both are binding, and nothing ranks a local rule against a system one. The resolution offered was that the file holds two kinds of claim: *this project is in creative mode* (about the project, and unable to drift, since the mode never changes) and *here is what the modes are* (about the system, and able to). Options: only the project's own mode binds; the whole file binds, pinned at initiation; the whole file binds, unranked. **Only the project's own mode.** The conflict dissolves rather than being adjudicated.

**The title.** Options: the mode and its consequence; the consequence alone; the mode alone. **The mode and its consequence** — the filename already carries the mode, but a title carrying only the directories would leave the word *creative* out of the line a person scanning the rules directory reads, and a title carrying only the mode states a label nobody can act on.

**Whether the two mode rules share a shape.** Options: one template filled; symmetric but each written for its mode; asymmetric, creative full and formal brief. **One template, filled** — the two can never diverge in structure and the text is substituted rather than composed. The accepted cost is that the formal fill restates the default at length, which every other rule already describes.

**Whether anything in it is the project's own.** Options: a slot for the developer's reason; nothing. **Nothing** — the file is fully determined by the mode, one of exactly two documents in the system apart from its date and footer. The accepted cost is that *why* a project chose its mode is recorded nowhere: not here, and not in the log, whose entries are one-line titles with no body.

**What was built.** The `a-project-works-in-formal-or-creative-mode` rule gained a *What the mode rule says* section carrying the template verbatim, filled for creative, in the way the announce-waytide-at-session-start rule quotes the session-start notice.

## Cycle 7 — whether the session-start notice reports the mode

**Hinge.** Open since initiation. The notice is the one surface rendered before every session, so anything in it is seen without being sought.

**Decision, given as direction.** **No.**

**A correction this forces, in cycle 1's record.** Cycle 1 recorded the cost of choosing a local rule as *the mode is not machine-readable, so `session-start.sh` cannot report it in the notice without parsing prose*. **That was overtaken by cycle 4**, which settled that the mode rule's **filename** carries the mode — readable by the same kind of directory read the hook already performs for the installed packages. So the notice **could** have reported it, and cycle 1's stated cost no longer holds. Declining is a judgment, not a limitation, and the record is corrected here rather than left with a stale impossibility standing where a decision belongs.

**The reasoning the system supplies.** The notice's lines all report **live or open state** — what is installed, and the experiments and features that have **not concluded** — and it grows only when there is something open. A mode is settled once and never changes, so a line reporting it would be identical every session for the life of the project. That is the failure the announce-waytide-at-session-start rule names in keeping the deferred queue out of the notice: a line that is always present is read once and never again.

**What was built.** The rule gained a section stating that the notice does not report the mode, that the obstacle is not capability, and that the mode is legible where every binding convention is — in the rules read at the start of the session.

## Cycle 8 — how the prompt fires for the projects that predate the mode

**Hinge.** The last question open since initiation. Cycle 3 settled that an absent mode rule means *never asked*, which is what keeps a deleted rule from silently reverting a project — and the accepted cost was that every pre-existing project inherits the question.

**Decision, given as direction.** **Out of scope for this feature.** Those projects are migrated explicitly, as a separate effort.

**The ordering constraint the agent surfaced.** The prompt fires the first time an agent opens a project after `foundation` carries the rule. So the migration must reach each project **before or with** the refresh that brings it the rule — otherwise the deferred work happens on its own, one project at a time, at whatever moment each is next opened, which is the opposite of an explicit migration. Publishing this feature and migrating are therefore not independent, and the publish is what starts the clock.

**What was built.** A deferred item, *The projects that predate the mode are migrated to an explicit mode rule*, ranked 1 in an otherwise empty queue and gated on this feature concluding and `foundation` being published. It records the ordering constraint, that all five projects are formal in fact so nothing about their behavior changes, and three questions it leaves open — whether it warrants a migration record, whether the mode is put to the developer per project or assumed, and whether the five are done in one pass.

**A small demonstration of the rule shipped earlier the same day.** The deferred item **names no project**, because naming one only for having installed the packages is what `a-project-does-not-name-its-consumers` forbids. Two of the five could have been named on other grounds and are not, since listing them beside the others would defeat the point. The registry outside the repository is where that list lives.

## State

**The feature completed on 2026-08-05.** Eight cycles, all attended. Two of them did not stand: cycle 2, replaced by cycle 3 when the developer found the silent revert, and cycle 1's stated cost, overtaken by cycle 4 and corrected in cycle 7. Both are kept as written.

Nothing below is open. What the feature deliberately left unresolved is recorded in the feature record's conclusion, and the one piece of work it hands on is the deferred item ranked 1.
