# Loop record — Skills

The skills feature delivers Waytide's commands as Claude Code skills, in a plugin named `we`. This record holds the cycles of its code: the installer's assembly of the plugin, and the loader's print of a pre-loaded rule by name, which a skill uses to load its rule.

**Mode:** unattended. The engineer first selected attended, then corrected it on 2026-11-03: do this unattended.

## Cycle 1 — Actuation of the assembly

**Hinge:** how a test runs the assembly of `.claude/skills/we/`.

**Decision:** the ordinary install run, `(cd "$project" && sh "$installer" agents-md)`, in the existing `test/automated/install.sh`. The plugin rule makes the assembly part of an install, as the placement of `.claude/settings.json` is part of one. A subcommand or a script of its own would add an interface that nothing yet needs. The existing test already actuates once, so each outcome of the assembly is one more observation of that actuation.

## Cycle 2 — Observation of the placed skills

**Hinge:** what the test reads about the placed skills.

**Decision:** the text of `SKILL.md` and of `help.md` at `.claude/skills/we/skills/some-command/`, each compared with its control text. The comparison of text reads the copy itself, so a file placed with the wrong content fails. A test of presence alone would not catch that.

## Cycle 3 — Layout of the plugin

**Hinge:** where a skill sits inside the plugin directory.

**Decision:** the standard plugin layout. The manifest is at `.claude-plugin/plugin.json`, and each skill is at `skills/<command>/`. The plugin rule names the plugin directory and its manifest. It does not name the place of the skills in it, and the standard layout is what Claude Code reads.

## Cycle 4 — Controls of the placed skills

**Hinge:** the known inputs.

**Decision:** a package `some-package` carrying `skills/some-command/SKILL.md` and `help.md`, written from control texts. The package is not a real one, so the test does not change when a real skill does.

## Cycle 5 — Implementation of the placed skills

**Hinge:** the code that copies the skills.

**Decision:** a direct implementation, `place_skills` in `install.sh`, run after `place_settings_json`. It removes `.claude/skills/we/` and builds it whole each time, because the plugin rule says a skill is changed in its package and never in the assembled directory. A directory with no `SKILL.md` is passed over.

## Cycle 6 — The manifest

**Hinge:** the observation, controls, and implementation of the manifest.

**Decision:** the test compares `plugin.json` with a control text naming the plugin `we`. The installer writes it from a `plugin_json` function, beside the `settings_json` function it resembles. The manifest is written only where a skill was placed, so a project whose packages carry no skills gets no empty plugin.

## Cycle 7 — A deactivated package's skills

**Hinge:** the observation, controls, and implementation of leaving out a deactivated package.

**Decision:** the controls add a package `some-other-package` with a skill, and a package-set declaration naming it `Inactive`. The test reads that its skill is absent from the plugin. The test was run before the implementation and failed, which shows it discriminates. The implementation reads the latest declaration's `Inactive` line with the same expression `load-rules.sh` uses, so the two agree on what is deactivated.

## Cycle 8 — The loader prints a pre-loaded rule by name

**Hinge:** how a skill loads a rule that is pre-loaded.

**Decision:** `load-rules.sh <rule-name>` searches the pre-loaded rules after the on-demand ones. The plugin rule says a skill loads its rule with the loader, and the log rule is pre-loaded, so the loader printed nothing for it. A skill that only named the rule would depend on the session-start read, which a compaction removes. The first implementation joined the end of one file's last entry to the next file. An entry now also ends at each file boundary.

## Cycle 9 — Naming

**Hinge:** the names of the outcomes.

**Decision:** *Places a package's skills in the plugin*, *Names the plugin we*, *Leaves out a deactivated package's skills*, and *Prints the named pre-loaded rule*. Each states what the installer or the loader does, in the form of the outcomes already in the two tests.

**Outcome:** `install.sh` assembles `.claude/skills/we/` from the active packages' skills. `load-rules.sh` prints a pre-loaded rule by name. The `/log` skill and its help are in `system/foundation/skills/log/`. Verified: every automated test.
